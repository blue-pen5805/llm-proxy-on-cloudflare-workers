# Repository Instructions

These instructions apply to the entire repository.

## Start with the project contracts

- Follow [Project Principles](docs/project-principles.md) for architecture and
  scope decisions.
- Read the relevant documents under `docs/design/` before changing request flow,
  provider behavior, authentication, configuration, key selection, or
  observability.
- Treat routes, configuration names, provider capabilities, security behavior,
  and documented limits as contracts. Keep implementation, tests, and
  documentation synchronized.

## Protect configuration and credentials

- Never edit `config.jsonc` or `config.<environment>.jsonc`. They are ignored,
  operator-owned files that may contain live credentials.
- Never add real keys, passwords, tokens, service-account data, or other
  credentials to source, examples, tests, documentation, logs, command output,
  or commit messages. Ask the operator to supply real values.
- Treat `.dev.vars*`, `.secrets-temp*.json`, and secret-deployment dry-run output
  as sensitive. Do not expose their values or add them to version control.
- Put safe placeholders for new settings in `config.example.jsonc`.

## Keep configuration artifacts synchronized

- When adding or changing a setting, update the schema, example configuration,
  runtime reader, applicable scripts, tests, and documentation as described in
  [Development and Verification](docs/development.md#adding-or-changing-configuration).
- After modifying `schemas/config-schema.json`, run `npm run cf-typegen`.
- Never edit `worker-configuration.d.ts` manually; it is generated by Wrangler.

## Maintain design documentation

- Update the relevant document under `docs/design/features/` whenever
  application behavior or architecture changes. Add a new feature document for
  a new core capability.
- Link new design documents from `docs/design/overview.md`. Link new user or
  contributor guides from `docs/index.md`.
- Write design documentation in English. Explain rationale and structure there;
  keep commands and task-oriented instructions in user or contributor guides.
- Cite current official documentation when behavior depends on Cloudflare or a
  provider API.

## Finish changes completely

- Add `CHANGELOG.md` entries only for changes to application functionality or
  externally observable runtime behavior. Do not add entries for documentation,
  contributor guidance, project policy, development process, tests, refactors,
  or maintenance that has no functional effect.
- When finishing a work session with changelog-worthy changes, derive the
  entries from the net difference between the state at the start of the session
  and the final state. Describe only the resulting functionality or behavior;
  do not record intermediate revisions, superseded directions, or approaches
  that were later reverted. Consolidate related work into concise entries,
  prepend them to the applicable section, order all entries in reverse
  chronological order, and include the change date in `YYYY-MM-DD` format.
- After making changes, assess the appropriate `package.json` version using
  semantic versioning based on the scope and compatibility impact. Propose the
  resulting version to the operator, and never update the version number
  without their explicit confirmation.
- Do not leave placeholder implementations or `TODO` comments unless the user
  explicitly requests them. Roadmap work belongs in `TODO.md`.
- Preserve unrelated worktree changes and never include local configuration or
  generated secret files in a change.
- Verify changes according to
  [Development and Verification](docs/development.md#required-verification) and
  report commands that were not run or did not pass.
